# Domain Glossary — RiscVSiriusStudio

A RISC-V assembly simulator packaged as a VS Code extension, for teaching computer architecture. This file is the project's ubiquitous language: when code, issues, or tests name a domain concept, use the term as defined here.

## Instruction model

- **DecodedInstruction** — a typed, read-only view wrapping one **Raw IR node**. The single source of truth for instruction facts (`usesRs1`, `usesRs2`, `usesRd`, `readsMemory`, `writesRegister`, `branchesOrJumps`, the write-back-value origin `writesComputedResult`/`writesLoadedValue`/`writesReturnAddress`, …) and for memory-access shape (`memoryAccess(): { bytes: 1 | 2 | 4, signed: boolean } | null`, plus a pure `extend(bits)` helper for sign/zero extension of loaded values). Constructed via `DecodedInstruction.from(rawNode)`. Lives in `src/vcpu/instruction.ts`. Replaces the stringly-typed predicates formerly scattered in `src/utilities/instructions.ts`. It **wraps — does not replace** — the parser/IR output; the assembler and `InternalRepresentation` are untouched. **CPU-independent**: it holds only **ISA facts** (see below) — never a **Control signal**. Every CPU model reads the same `DecodedInstruction`. (Seam recorded in `docs/adr/0001-decodedinstruction-is-cpu-independent.md`.)

- **Raw IR node** — the untyped (`any`) instruction object emitted by the assembler (`src/utilities/riscvc.ts`, itself wrapping the peggy-generated `riscv.ts` parser). Carries `.type` (`R/I/S/B/U/J`), `.opcode` (bitstring), `.encoding.funct3`/`.encoding.funct7`, `.rs1/.rs2/.rd.regeq` (register names), `.instruction` (mnemonic string), `.inst` (numeric PC), `.asm` (source text). `DecodedInstruction` reads through it lazily. Note the name clash: the raw node's `.instruction` field is the *mnemonic*, not a DecodedInstruction — hence the fuller class name.

- **Memory-access shape** — the `{ bytes, signed }` classification of a load/store, derived once from `funct3`. Replaces three divergent `switch(funct3)` decoders (previously in `singlecycle.ts`, `pipeline.ts`, `Simulator.ts`). The CPU still performs the actual `DataMemory.read/write`; `DecodedInstruction` owns only the classification and the pure `extend` of loaded bits.

## Instruction facts vs control signals

- **ISA fact** — a property of a RISC-V instruction that is true regardless of the CPU that runs it: its type, register usage, funct fields, memory-access shape, extension rule, and the origin of its write-back value. ISA facts are the *only* thing `DecodedInstruction` exposes, and every CPU model shares them.
  _Avoid_: "decode result", "control info".

- **Control signal** — a value that drives a *specific* datapath's wires and muxes: `alu_op`, `imm_src`, `ru_data_wr_src`, `br_op` (the `ControlSignals` shape in `src/vcpu/components/decoder.ts`). Datapath-specific, so it lives in a **ControlUnit**, never in `DecodedInstruction`. A different microarchitecture (e.g. two ALUs) gets its own ControlUnit reading the same ISA facts.
  _Avoid_: "instruction fact", using an `alu_op`/mux string as though it were ISA.

- **ControlUnit** — the per-microarchitecture translator from `DecodedInstruction` (ISA facts) to a `ControlSignals` set (datapath control). One per datapath: the single-cycle and pipeline CPUs share one because they share a functional datapath.

## CPU stepping seam (ICPU)

> **Status: implemented.** This is the model the ICPU deepening (architecture-review candidate #3) delivered: `cycle()` self-commits and returns a **Cycle effect**, the **Datapath view** lives off ICPU, and the editor highlight derives from the Cycle effect's retiring instruction (no `highlightedInstruction()` on the contract). The governing ADRs: `docs/adr/0002-cycle-is-self-committing.md`, `docs/adr/0003-datapath-view-is-off-icpu.md`, `docs/adr/0004-editor-highlight-from-cycle-effect.md`; migration tickets in `.scratch/icpu/`.

- **ICPU** — the shared engine contract every CPU model (single-cycle, pipeline) implements (`src/vcpu/interface.ts`). It exposes *stepping and architectural state* — `cycle()`, `getPC()`, `finished()`, and the register-file / data-memory / program accessors — and nothing datapath-shaped (no render wires; see **Datapath view**) and no view query (the editor highlight derives from the **Cycle effect**, not the contract — ADR-0004). One `cycle()` call advances exactly one clock.

- **Self-commit** — `cycle()` owns advancing its CPU's own architectural state: register file, data memory, program counter. Its return value is an *observation* of what the clock committed, never a computation the caller must replay to make state advance. PC advance (jump vs. next) and halt (`ebreak`) detection are internal; `finished()` reflects halt.
  _Avoid_: committing register/memory/PC in the Simulator by reading a CPU's result — the leak this seam removes (pre-migration single-cycle did exactly that).

- **Cycle effect** — the CPU-independent, per-clock observation returned by `cycle()`: the **retiring instruction**, at most one register write, at most one memory access (read or write), and the control transfer (next PC / taken) — each tagged with the `DecodedInstruction` that produced it. Per *clock*, not per *instruction*: in the single-cycle CPU every field shares one instruction; in the pipeline CPU the register write comes from the instruction in **WB** and the memory access from the (different) instruction in **MEM**. Drives the Simulator's register/memory notifications for both the text and graphic simulators.
  - **retiredInstruction** — the instruction that retired (committed) this clock: single-cycle → the executing instruction; pipeline → the **WB**-stage instruction; **absent** during a pipeline fill or bubble (nothing retired). The view layer highlights its source line — the editor highlight is a *view decision driven by this observation*, not an engine query (ADR-0004). Because it is the retiring instruction, the highlighted line and the register/memory notification always name the same instruction each clock.
  _Avoid_: "step result" — the Simulator's `step()` wraps `cycle()`, so "step" names the outer layer; treating a Cycle effect as one instruction's total effect. Making the editor highlight a query on ICPU (the removed `highlightedInstruction()`) rather than a view decision over `retiredInstruction`.

- **Datapath view** — the per-CPU, render-only snapshot of a datapath diagram's values for one clock: `MonocycleWires` for the single-cycle datapath (the combinational wire bundle — `add4`, `ru`, `alu`, `buMux`, `wb`, …) and `PipelineStages` for the 5-stage pipeline (the `IF`/`ID`/`EX`/`MEM`/`WB` latches). Captured **during** `cycle()` (combinational wires are valid only at cycle time) and consumed **only** by the graphic simulator client (`client/simulator/src/context/graphic/`). It is **CPU-specific and lives off ICPU** — reached through a statically-typed concrete CPU reference, never a downcast on CPU kind. The text simulator never sees it. Takes over the render role of today's `SCCPUResult` / `PipelineCycleResult`. (Seam recorded in `docs/adr/0003-datapath-view-is-off-icpu.md`.)
  _Avoid_: putting it on ICPU as a `kind`-discriminated union or an opaque payload; calling it a "result" (it observes wires; it is not the CPU's output).

- **Editor highlight** — the source line lit in the editor each clock. It is a **view decision**, not an ICPU query: the view highlights the line of the Cycle effect's **retiredInstruction** (see above). Single-cycle lights the just-retired (executing) line; pipeline-**text** lights the **WB/retiring** line — so the highlight and the register/memory notification agree each clock. Pipeline-*graphic* drives no editor highlight (it renders the five stage latches). The **initial** highlight, before the first `cycle()`, has no effect to read: monocycle lights `program[getPC()]` (its start-cursor); pipeline lights nothing. History: this replaced an ICPU accessor `highlightedInstruction()` (formerly `currentInstruction()`), whose pipeline meaning was the *fetched* (IF/ID) line — see `docs/adr/0004-editor-highlight-from-cycle-effect.md` and `.scratch/icpu/deferred/highlightedinstruction-removal.md`.
  _Avoid_: re-adding a "what to highlight" query to ICPU; highlighting the *fetched* line in pipeline-text (breaks agreement with the notification).

## Client view seam (Shell / DatapathPane)

> **Status: decided, not yet built.** The React client mirrors the engine's ICPU/**Datapath view** split (ADR-0003) across the postMessage boundary. Today one React app multiplexes both CPUs through one `CurrentInstContext` and duck-types monocycle vs pipeline on `message.result.IF`; this seam removes that. Governing ADR: `docs/adr/0005-client-datapath-pane-seam.md`.

- **Shell** — the CPU-independent React view: the one-copy layer that renders everything reacting only to *what committed this clock* — the registers table, data-memory table, the static read-only instruction-memory table, the editor and its highlight, the side panels, and the run/step/reset controls. Its sole per-clock input is the **Cycle effect** (plus the initial program/memory load); it holds no datapath render data and never references `MonocycleWires` / `PipelineStages`. The client peer of the **text simulator** — both consume only the Cycle effect and architectural state. Because the shared tables carry no pipeline-specific detail (no forwarding highlight, no stage tag), the Shell can exist once rather than duplicated per CPU.
  _Avoid_: a Shell component reaching into a **Datapath view** for pipeline-only decoration (re-leaks per-CPU shape into the shared layer — the exact defect this removes); duplicating the Shell into two whole React apps.

- **DatapathPane** — the per-CPU render seam on the client: a slot the **Shell** renders, blind to which CPU fills it. Two adapters sit behind it — `MonocycleDatapathPane` (reads `MonocycleWires`) and `PipelineDatapathPane` (reads `PipelineStages`, and owns the pipeline-stages table). The client peer of a concrete CPU's `datapathView()`. Selection happens **once, at mount** (the host declares the running CPU), so each pane is statically typed to its CPU and there is nothing to discriminate at step time — the `.IF` sniff and the divergent hand-mirror types (`ResultState`, `PipelineCycleResult`) become structurally impossible. Genuinely shared machinery (the enabled-vs-all edge diff, the `EdgeId` registry, wire-animation primitives) is extracted into a shared datapath-primitives module both panes import — **not forked**.
  _Avoid_: a `kind`-discriminated `step` payload or duck-typing on `.IF`; each pane re-declaring the engine's render types instead of importing them from the one protocol module; forking the two connection controllers rather than sharing primitives.

- **SimulatorTable** — the one deep table module the **Shell** renders every table through: the registers table, the data-memory table, and the read-only instruction-memory table are each an *adapter* of it, differing only by their columns and row data. It is **declarative** — columns and rows go in, edits come out — and keeps the Tabulator library **hidden** behind that interface: no caller holds a Tabulator instance. Replaces today's four copy-pasted table-lifecycle setups and the near-duplicate memory components. Transient per-clock cell animation (the write/read flash) is the one imperative concession, reached through a small ready-handle rather than the declarative surface.
  _Avoid_: a per-table copy of the create/destroy/update lifecycle; a `SimulatorTable` that knows its callers by name (a `kind`/`preset` discriminator) instead of taking columns as data; leaking Tabulator's instance to callers; calling it a "table component" (it is the shared module the per-table adapters are built on).
